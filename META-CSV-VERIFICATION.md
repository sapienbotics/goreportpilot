# Meta Ads CSV — end-to-end verification

Date: 2026-08-23
Commit: `a29acf4`

**Verdict: a real Meta Ads Manager export maps cleanly, but it did not before
this pass.** Two defects would have shipped wrong numbers or a silently
degraded deck, and both are fixed. Four further issues are logged, one of
which puts a wrong-looking figure on the deck today.

---

## 1. The fixture

`backend/tests/fixtures/csv_ingest/meta_ads_export_july2026.csv` — 124 rows
(4 campaigns × 31 days), 20 columns, generated by
`gen_meta_ads_fixture.py` so the numbers are reproducible and every aggregate
below is auditable rather than asserted.

### Column names — sourced, not guessed

Meta does not publish a CSV schema, and the how-to blogs describe metrics
conceptually without ever showing a header row. The names came from R-mangled
headers in a real-world Facebook-ads dataset ([RickPack/FBadstats](https://github.com/RickPack/FBadstats)),
whose `make.names()` output preserves the originals unambiguously —
`AMOUNT.SPENT..USD.` can only be `Amount spent (USD)`,
`CTR..LINK.CLICK.THROUGH.RATE.` only `CTR (link click-through rate)`,
`RESULT.INDICATOR` only `Result indicator` — cross-checked against Meta's
documented Ads Manager column set and its `—` convention for unavailable
cells.

**Independent corroboration:** this repo's pre-existing
`meta_ads_multisheet.xlsx` fixture, written before this engagement, uses
`Reporting starts`, `Amount spent (INR)` and `Results`. Two unrelated sources
agreeing on the names is stronger than either alone.

The one judgement call is capitalisation: FBadstats is uppercased by R, so it
cannot settle case. I used Meta's sentence case (`Amount spent (USD)`), which
matches the Ads Manager UI the export mirrors, and the pre-existing fixture.

### Quirks included

| Quirk | As it appears |
|---|---|
| currency in the header | `Amount spent (USD)` — never in the cells |
| date pair | `Reporting starts` / `Reporting ends`, identical per row |
| CTR as a bare fraction | `0.009569`, no `%` sign |
| conversions renamed | `Results`, plus a `Result indicator` column |
| em-dash nulls | `—` on 3 fully-paused campaign-days (39 cells) |
| hierarchy | `Campaign name` / `Ad set name` / `Ad name` |
| em-dash inside text | ad names like `Carousel — Spring Offer` — the null sentinel and real content share a character |

The last one was not deliberate at first and turned out to be the most useful:
it proves the em-dash handling keys on the cell, not on the character.

### True aggregates

| Metric | True value |
|---|---|
| Impressions | **6,921,544** |
| Link clicks | **74,372** |
| Results | **3,240** |
| Reach (summed) | **5,186,231** |
| Amount spent | **$46,956.26** |
| CTR | **1.0745%** (0.010745 as a fraction) |
| CPC | **0.6314** |
| CPM | **6.7841** |
| Cost per result | **14.4927** |

*Caveat worth stating: summing `Reach` across days overcounts, because reach
is deduplicated people and the same person recurs daily. The fixture is
internally consistent, but no daily export can produce a true period reach —
that is a Meta API limitation, not ours. Frequency inherits it.*

## 2. Pipeline results

### Every question, answered

**Was the currency read from the `(USD)` header pattern?**
**Yes** — `currency: USD, source: column header`. The deck rendered
`$46,956.26` with the account currency deliberately set to **INR**, so the
per-source currency is genuinely winning rather than coincidentally agreeing.

**Was CTR-as-decimal rendered as a percentage?**
**Yes**, and by a stronger route than scaling. The mapper labelled it
`percent`; the normaliser did not scale the raw `0.009569` at all but
**recomputed** CTR as Σclicks/Σimpressions×100 = **1.0745%**, exactly the true
value. The `0.0047 → 0.47%` scaling path still exists for a file whose
components are absent — the pre-existing `meta_ads_multisheet.xlsx` fixture
exercises it and discloses the conversion in a warning.

**Was `Results` mapped to conversions, or did it need an ambiguity?**
**It raised an ambiguity, correctly**, and blocked the commit:

> "What specific action or event does 'Results' represent in this export?
> (e.g. purchases, video views, leads)" — candidates: `conversions`,
> `video_views`, `other objective-based results`

That is the right call: in Meta, `Results` genuinely means whatever the
campaign objective was, and two campaigns in one export can have different
ones. `Cost per result (USD)` raised a second, matching ambiguity. Both
mapped at confidence 0.70, and are now correctly blocked by the `<=`
threshold fix from the previous pass.

*Observation, not fixed:* the file **contains the answer**. The
`Result indicator` column reads
`actions:offsite_conversion.fb_pixel_purchase` on every row — these are
purchases. The mapper ignored that column as "not a metric" (true) without
using it to resolve the question (a miss). Feeding indicator values into the
ambiguity prompt would let the model answer its own question. Logged as a
future improvement rather than changed here.

**Were em-dash nulls handled like the LinkedIn blanks?**
**Yes, identically.** All 124 rows were read; the 39 em-dash cells parsed to
NaN and were skipped by `_sum_over`'s NaN filter rather than counted as zero —
the same path as LinkedIn's 9 blank cells. Three fully-paused campaign-days
contributed nothing rather than dragging averages down. Ad names containing
em-dashes were unaffected.

**Which date column was chosen?**
`Reporting starts`, with `Reporting ends` ignored — **but only reliably after
a fix**. See below; this was the most serious finding.

### Rendered KPI values vs true aggregates — read from the deck

Read back out of the generated `.pptx` by shape geometry, not recomputed:

| Rendered label | Rendered value | True | ✓ |
|---|---|---|---|
| RESULTS | `3,240` | 3,240 | ✓ |
| REACH | `5,186,231` | 5,186,231 | ✓ |
| IMPRESSIONS | `6,921,544` | 6,921,544 | ✓ |
| FREQUENCY | `1.33%` | 1.3346 | **value right, unit wrong** |
| AMOUNT SPENT | `$46,956.26` | 46,956.26 | ✓ (and `$`, not `₹`) |
| LINK CLICKS | `74,372` | 74,372 | ✓ |

All ten aggregates match the generator exactly (delta 0.0000). The one defect
is `FREQUENCY 1.33%` — see finding C.

## Findings

### A. FIXED — `cost_per_result` was 7× wrong

Meta calls a conversion a "result", so `cost_per_result` had no declared
derivation and fell to the volume-weighted mean: **101.06 against a true
14.49**. The weighting was by impressions, and the awareness campaign — huge
impressions, almost no results — dominated it.

This is the original ratio-metric bug reappearing purely because of
vocabulary. It vindicates the registry design (the fallback prevented
something far worse than a mean — summing would have been absurd) while
showing the registry needs each platform's dialect. Aliased
`cost_per_result` → `cost_per_conversion`; `results` already resolved as a
conversions component, so it now recomputes as Σspend/Σresults = **14.4927**.

Also added: `frequency` = Σimpressions/Σreach, with `reach` as a declared
component distinct from impressions. Was 1.3415 weighted, now **1.3346**
exact.

### B. FIXED — the model dropped the date column in 3 of 5 runs

The most serious finding, and it only appeared because I ran the live model
more than once.

`Reporting starts` / `Reporting ends` reads like report *metadata* — the
window the report covers — and at account level that is exactly what it is.
On a daily breakdown it is the day. GPT-4.1 cannot tell those apart from eight
samples, and returned **no date column at all** in 3 of 5 live runs on the
same file:

```
run  date_column        entity_column
1    None               Ad name
2    None               Ad name
3    None               Ad name
4    Reporting starts   Campaign name
5    Reporting starts   Campaign name
```

When that happens, the trend chart, every change badge, and all trend language
in the narrative vanish **together** — and the deck still renders. Flat, plausible,
with nothing to indicate anything is missing. A user would have no way to know
they got a worse report than the same file produced yesterday.

The profiler had already measured the thing the model was guessing at:
whether the column's values vary. A column of 31 distinct dates across 124
rows is a time dimension whatever its header says — that is measurement, not
classification, so it belongs in code rather than a prompt.
`mapper._finalise()` now falls back to the date-typed column with the most
distinct values when the model names none. **5 of 5 runs now resolve
`Reporting starts`** (three at 0.75 confidence, the fallback firing at exactly
the earlier failure rate).

### C. LOGGED, NOT FIXED — `FREQUENCY` renders as `1.33%`

`_slide_unit()` collapses the `ratio` unit onto `percent`, so `_fmt_csv_value`
appends a `%`. Correct for a CTR stored as 0.0047; wrong for a multiplier.
Frequency 1.33 means each reached person saw the ad 1.33 times; "1.33%" is not
a quantity that exists. **ROAS has the same shape** — a 3.5× return would
render "3.5%".

The value is right and only the suffix is wrong, which is the more dangerous
kind of error because nothing looks broken. The fix is a fourth display unit
("multiplier"), which changes rendering for every existing ratio metric — so
I have flagged it rather than changed it. Tech-debt item 8 carries the
proposed implementation and a cheaper interim (treat a ratio-unit value > 1 as
a multiplier, since a real percentage stored as a fraction is ≤ 1 after
scaling).

**This is the one thing on the attached deck I would not send to a client.**

### D. LOGGED — no template can display a CSV change badge

None of the six `.pptx` templates has a `{{csv_kpi_N_change}}` placeholder —
only `label` and `value`. `_populate_csv_slide()` computes `change_str`,
including the explicit-`change` handling added when the full-period headline
landed, and has nowhere to put it. The within-period trend is computed,
reaches the narrative (where it is used correctly), and is dropped at render.

Not a regression from item 4a: the generic slide previously showed "—" for
these metrics anyway, since `previous_value` is None for a single upload.
Fixing it means editing six binary templates — a design task, not a code one.

### E. LOGGED — entity column is unstable under a hierarchy

Across five runs the model chose `Campaign name` twice and `Ad name` three
times. Both are defensible and the numbers are right either way, but the
report's "top entries" change identity between runs of the same file, and a
saved mapping locks in whichever won. Worth deciding whether to prefer the
coarsest level by default or make it an explicit question.

### F. LOGGED — `_parse_localized` prints to stdout

529 lines of `Could not parse numeric value: ...` against 59 lines of actual
report in one run. It is normal type-inference probing, emitted with `print()`
instead of `logger.debug()`. In production it goes to Railway's logs,
compounding tech-debt item 2 — and it actively obstructs the rule below.

## 3. Narrative quality — does Meta match LinkedIn?

**Yes, and slightly better**, because Meta's export carries cost-per-result
natively so the model has efficiency to talk about, not just volume.

Full narrative is in the attached deck. Every entity-attributed figure was
audited against that entity's own line in the prompt:

| Narrative claim | Entity's own data | ✓ |
|---|---|---|
| Lookalike impressions +24.7%, clicks +23.9% | +24.7%, +23.9% | ✓ |
| Lookalike spend +26.1% | +26.1% | ✓ |
| Lookalike CTR "slipped to 1.67%" | 1.67%, −0.7% | ✓ |
| Retargeting CTR 4.12%, CPC $0.31 | 4.12%, 0.31 | ✓ |
| Retargeting 17,089 link clicks | 17,089 | ✓ |
| Video Views impressions −2.0%, clicks −2.2% | −2.0%, −2.2% | ✓ |
| Video Views CTR 0.47% | 0.47% | ✓ |
| Results 1,459 → 1,666, +14.2% | first/second half | ✓ |
| Cost per result $14.72 → $14.28, −3.0% | first/second half | ✓ |

No aggregate attached to a named entity; no invented absolute values; correct
currency throughout; the change consistently described as a within-July trend
rather than growth against a prior month.

## 4. Deck-quality items

### (a) FIXED — generic KPI slide suppressed when redundant

`_kpi_scorecard_is_redundant()` in `slide_selector.py`. The scorecard is
dropped only when **every** label on it appears on a **single** upcoming
source slide. Deliberately conservative:

- any GA4/Meta/Google/GSC figure puts a label on the scorecard that no CSV
  slide carries → kept;
- labels spread across two sources are not a subset of either, and the
  scorecard is then the only place they appear together → kept;
- an empty scorecard is not treated as redundant, because dropping a slide for
  having no content is a different decision from dropping it for duplication.

Verified on three shapes:

| Report | Scorecard | Slides |
|---|---|---|
| CSV-only | **suppressed** | cover, exec summary, csv_data, wins, concerns, next steps |
| CSV + GA4 | **kept** (SESSIONS/USERS aren't on the CSV slide) | + kpi_scorecard, website_traffic |
| No CSV | **kept** | unchanged |

The live Meta deck is 6 slides with no blank left behind.

### (b) FIXED — an entity may not be a bare win and a bare concern

The `concerns` instruction now forbids reusing an entity credited in
`key_wins` **unless the bullet states the tension in the same sentence**.

The live deck exercises exactly this. Two campaigns appear in both, and both
name the tension rather than contradicting themselves:

> ✓ *Lookalike 1% | Purchasers grew impressions 24.7% and link clicks 23.9%…*
> ⚠ *Lookalike 1% | Purchasers grew spend 26.1%, **outpacing results growth**, so efficiency needs close monitoring.*

> ✓ *Retargeting | Site Visitors 30d maintained a 4.12% CTR and a low $0.31 CPC…*
> ⚠ *Retargeting | Site Visitors 30d **improved CTR but delivered only 17,089 link clicks** — expand audience to scale impact.*

This is the better outcome than a blunt ban: "efficient but too small to
matter" is a more useful sentence than either half alone.
